# CoSIL 复现实验两次失败问题报告

**报告日期：** 2026-09-30  
**实验范围：** SWE-bench-Verified 与 SWE-Explore 的交集，共 451 个实例；仅进行定位实验。  
**目标输出：** file mapping；后续可在不重新调用模型的情况下，将同一批候选结果重新格式化为 function span。  
**当前结论：** 首次运行结果不能作为正式结果使用。第二次问题已经完成代码修复和小规模验证，修复后的全量运行已重新启动。

## 1. 摘要

本次复现先后出现了两类问题。它们都发生在 CoSIL 的“仓库结构生成—检索工具—结果解析”链路上，而不是 SWE-bench 被测项目本身的代码问题。

| 问题 | 直接原因 | 主要影响 |
| --- | --- | --- |
| 问题一：相对路径解析错误 | CoSIL 子进程的工作目录与数据集中的相对仓库路径不一致 | 所有实例生成的仓库结构均为空；模型无法获得正常的仓库文件候选 |
| 问题二：修复路径后仍读取旧缓存，并且 file 解析会回退到函数结果 | 主定位代码和 `FL_tools` 使用了不同的结构缓存路径；解析器把 `found_related_locs` 混入了 file 模式 | 外部新缓存虽非空，但工具层仍可能读到旧的空缓存；部分 file mapping 结果实际上是函数粒度结果 |

因此，第一次运行中出现的非零 Precision、Recall、F1 和 Context Efficiency 并不代表 CoSIL 完成了正常的仓库检索。它们主要来自后处理阶段对模型返回的函数名称进行本地 AST 解析，以及不同粒度结果被混合统计，不能与论文结果直接比较。

已有的首次路径问题单独记录见：[结构生成路径问题报告](../reports/2026-09-29-structure-generation-path-bug.md)。本文进一步将两个问题放在同一条执行链路中说明，并记录第二次问题的修复和验证方式。

## 2. 预期执行链路

本实验的正常流程应当是：

```text
本地仓库快照
    │
    ▼
create_structure(仓库绝对路径)
    │
    ▼
每个实例的非空 repository structure / AST-like structure
    │
    ├── 文件级定位：模型选择文件，解析 found_files
    │
    └── 函数级定位：模型调用 FL_tools 获取文件、类、函数代码，解析 found_related_locs
    │
    ▼
统一转换为代码区域并计算指标
```

这条链路有两个必须保持一致的契约：

1. 结构生成器、主定位逻辑和工具层必须读取同一个实例结构文件。
2. file mapping 只能使用文件级字段，function span 只能使用函数级字段，不能在解析失败时静默跨粒度回退。

## 3. 问题一：相对路径导致所有结构为空

### 3.1 触发方式

数据集记录中的仓库路径类似：

```text
repos/astropy__astropy-12907
```

这个路径是相对于实验项目根目录定义的。适配器启动 CoSIL 子进程时，将工作目录设置为：

```text
third_party/CoSIL
```

但结构生成代码仍直接调用：

```python
create_structure("repos/astropy__astropy-12907")
```

于是实际解析的目录变成了：

```text
third_party/CoSIL/repos/astropy__astropy-12907
```

而真实仓库位于实验项目根目录下的对应路径。两者不是同一个目录。

### 3.2 为什么程序没有报错

CoSIL 的结构生成逻辑底层使用 `os.walk()`。当传入目录不存在时，`os.walk()` 可以直接返回空迭代结果，而不是抛出异常。随后结构生成函数把空结果保存成：

```json
{}
```

因此：

- 子进程退出码仍然是 0；
- 结构 JSON 文件确实被创建；
- 但文件内容没有任何仓库节点；
- 原有流程没有检查“结构是否为空”，所以把它当成成功缓存继续使用。

这也是为什么只检查命令是否成功、日志是否有 JSON 文件，无法发现该问题。这里发生的是“语义失败”，不是“进程失败”。

### 3.3 观测到的现象

首次运行审计时发现：

- 451 个 file-level 记录的 `found_files` 全部为空；
- 大多数 function-level 记录仍有 `found_related_locs` 字段，但这并不代表 CoSIL 成功从仓库结构中检索到了函数；
- 结构文件存在，但顶层结构为空；
- 工具调用中出现找不到文件、找不到函数或返回空内容的情况。

从数据链路看，空结构导致可供 CoSIL 使用的文件集合为空。模型即使在原始文本中生成了一个看起来合理的文件名，也会在候选文件过滤阶段因为“不在可用文件集合中”而被丢弃。

### 3.4 为什么最终仍有非零指标

这是本次问题最容易造成误判的地方。适配器的后处理逻辑中存在一条独立于 CoSIL 结构检索的路径：

1. 从模型原始响应中提取函数名或函数定位文本；
2. 在本地真实仓库源文件上调用 Python `ast.parse`；
3. 根据函数名找到起止行号；
4. 把该行号转换为最终预测区域。

这一步使用的是本地源代码的 AST 解析，不是 CoSIL 生成的 repository structure，也不是模型在检索阶段看到的上下文。因此它可以在 CoSIL 结构为空时仍然产出一部分代码区域。

换句话说：

```text
CoSIL 结构检索失败
        │
        ├── 正常检索结果：基本为空
        │
        └── 后处理根据函数名重新扫描本地源文件：仍可能得到行号
```

因此首次审计中出现的非零结果，例如 Precision 68.39%、Recall 42.24%、F1 44.16%、Context Efficiency 85.10%，只能说明后处理找到了一些与标注重叠的区域，不能证明模型获得了正确的仓库上下文。首次结果已标记为无效，不纳入正式结论。

### 3.5 问题一的根因

问题一不是 AST 算法本身失败，而是路径解析契约没有统一：

```text
数据集路径语义：相对于实验项目根目录
CoSIL 进程语义：相对于 third_party/CoSIL
实际结果：同一个字符串指向了不同目录
```

同时，流程缺少以下保护：

- 传入结构生成器前统一转为绝对路径；
- 生成后检查结构必须非空；
- 空结构禁止进入后续定位流程；
- 缓存中已有空 JSON 时必须失效并重建。

## 4. 问题二：新结构已生成，但工具层仍读取旧缓存

### 4.1 问题一修复后的状态

第一次修复将结构生成路径改为真实仓库的绝对路径，并将新结构保存到实验结果目录，例如：

```text
results/intermediates/cosil_retest/repo_structures/
```

预检查表明，新生成的结构已经非空。例如 `astropy__astropy-12907` 的结构包含多个顶层节点，文件数量约为 910，能够找到预期源文件、导入信息和函数代码。

这说明“结构生成”这一步已经修复，问题不再是所有 AST-like structure 都为空。

### 4.2 缓存路径没有完全统一

适配器已经将：

```text
PROJECT_FILE_LOC
```

指向新的外部结构缓存目录，主定位代码可以通过这个变量读取非空结构。

但 `third_party/CoSIL/CoSIL/fl/FL_tools.py` 中原先存在多处硬编码读取：

```python
load_json(f"./repo_structures/{instance_id}.json")
```

这些调用使用的是当前工作目录。由于 CoSIL 子进程的工作目录是 `third_party/CoSIL`，它们实际读取：

```text
third_party/CoSIL/repo_structures/{instance_id}.json
```

而不是适配器刚刚生成的：

```text
results/intermediates/cosil_retest/repo_structures/{instance_id}.json
```

因此形成了“两个结构来源”：

```text
主定位逻辑 ──────► 新的、非空的外部缓存

FL_tools ─────────► CoSIL 工作目录下旧的、可能为空的缓存
```

### 4.3 受影响的工具

受影响的工具读取包括：

- `get_functions_of_class`
- `get_functions_of_file`
- `get_classes_of_file`
- `get_code_of_file`
- `get_code_of_class`
- `get_code_of_class_function`
- `get_code_of_file_function`
- `get_all_of_files`
- `get_imports_of_file`

其中 `get_all_of_files()` 的影响尤其直接：如果它读到空结构，模型生成的文件名会再次因为不在工具返回的文件集合中而被过滤。函数、类和代码读取工具则会出现错误文件、错误函数或空代码结果。

在第二次部分复测中，结构文件本身已经非空，但只有很少的 file-level 记录被成功解析出文件候选；同时工具日志仍出现大量错误文件/函数调用。这与“结构生成成功、工具读取了另一份旧缓存”的现象一致。

### 4.4 解析器又掩盖了这个问题

原来的 `parse_cosil_jsonl(..., mode="file")` 逻辑大致是：

1. 优先尝试 `found_files`；
2. 如果 `found_files` 为空，则继续尝试 `found_related_locs`；
3. 将函数相关位置转换为代码行区域返回。

这会把 function span 当成 file mapping 的补救结果。最终的 file 输出因此可能混合两种粒度：

```text
真正的文件区域：文件起始行到文件结束行
函数区域：单个函数的起止行
```

这样即使 file mapping 的文件候选为空，最终结果仍可能看起来“有预测”，但它已经不是严格意义上的 file mapping。统计指标也会失去可比性。

正确规则应当是：

- `mode="file"`：只接受 `found_files`；为空就返回空，不跨粒度回退；
- `mode="function"`：只接受 `found_related_locs`；
- 如果需要同时保留两种结果，应输出两个明确分开的 JSONL 文件，而不是在解析器内部隐式混合。

## 5. 两个问题之间的关系

这两次问题不是同一个错误的重复，而是发生在不同阶段：

```text
问题一：结构生成输入路径错误
    └── 结构生成阶段就得到 {}

问题二：结构生成虽然修复，但读取方没有使用同一缓存
    ├── 主定位逻辑读新缓存
    ├── FL_tools 读旧缓存
    └── file 解析器又把函数结果作为回退
```

因此，第二次修复不能只检查结构 JSON 是否非空。必须同时检查：

1. 结构生成读的是正确仓库；
2. 主定位代码和所有工具读取的是同一份结构；
3. 工具返回了真实文件/类/函数内容；
4. file 和 function 结果没有跨粒度混用；
5. 原始响应、工具轨迹和中间结构能够相互审计。

## 6. 已采取的修复

### 6.1 路径和结构生成

- 在进入 CoSIL 前将仓库路径解析为绝对路径；
- 结构生成后检查顶层结构和文件数量，空结构直接判定失败；
- 空结构缓存不再被视为有效缓存；
- 每次重测使用独立的结构中间文件目录，避免旧缓存污染；
- 保留每个实例生成的结构文件，便于后续查看和复核。

### 6.2 工具层缓存读取

将 `FL_tools.py` 中分散的相对路径读取统一为一个结构加载函数。该函数按以下顺序工作：

1. 优先读取环境变量 `PROJECT_FILE_LOC` 指定的目录；
2. 未设置时，使用相对于 CoSIL 源文件位置解析的默认目录，而不是依赖进程当前工作目录；
3. JSON 不存在或结构为空时直接报错；
4. 所有文件、类、函数和导入工具都通过同一加载入口读取。

这样可以保证主定位逻辑与 `FL_tools` 使用同一份实例结构。

### 6.3 结果解析

- file 模式只解析 `found_files`；
- function 模式只解析 `found_related_locs`；
- 不再让 file 模式静默回退到函数结果；
- 需要比较两种粒度时，分别保存和统计，不在一个输出文件中混合。

### 6.4 运行留痕

重测保留以下内容：

- 原始模型响应和 CoSIL trajectory；
- 工具调用日志及错误重试记录；
- 每个实例的 repository structure / AST-like 中间文件；
- 运行日志、进度和失败实例列表；
- 最终 file mapping 输出，以及后续重新格式化得到的 function span 输出。

公共仓库不包含 `.env`、API key、服务地址或实际部署编号；报告中统一使用实验配置中的公开模型名 `gpt-5.4`。

## 9. 对复现实验有效性的结论

在问题一和问题二修复前：

- 不能认为模型看到了完整仓库结构；
- 不能认为工具调用成功提供了文件、类和函数上下文；
- 不能把函数后处理得到的区域当成 file mapping；
- 不能将对应 Precision、Recall、F1 或 Context Efficiency 与论文结果直接比较。

只有在修复后的全量运行满足“非空结构、统一缓存、工具成功读取、粒度严格分离、日志可审计”这五项条件后，结果才可作为正式复现结果，并进一步与 SWE-Explorer 论文的同粒度指标进行比较。

## 10. 复现经验

本次问题说明，仓库级定位实验不能只验证进程退出码和最终 JSONL 是否存在。至少需要在正式运行前加入以下语义级检查：

- 随机抽取实例，确认结构包含真实文件；
- 随机调用文件、类、函数和导入工具，确认返回非空内容；
- 检查所有读取路径是否来自同一配置；
- 对 file/function 输出做粒度断言；
- 把空结构、空候选和工具错误视为需要调查的失败，而不是正常的低质量预测；
- 保留中间结构和完整 trajectory，确保最终指标可以追溯到模型实际看到的上下文。
